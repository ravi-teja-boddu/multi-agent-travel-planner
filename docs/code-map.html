Stop 1

The big picture

Think of the program as a small travel agency. A receptionist (the orchestrator) reads your request and passes it to the right specialists. One specialist books flights and hotels, the other plans trips. They can work at the same time. Finally an editor (the synthesizer) combines their notes into one answer.

flowchart LR
    U["You type a question"] --> O["Orchestrator<br/>decides who should answer"]
    O --> S["Search agent<br/>flights and hotels"]
    O --> P["Planner agent<br/>tips and itineraries"]
    S --> SY["Synthesizer<br/>merges the answers"]
    P --> SY
    SY --> A["One final answer"]

If your question only needs one specialist, only that one runs, and the synthesizer passes its answer straight through.

What happens when you run python main.py

Python runs main.py from the top. The last lines, if __name__ == "__main__": sys.exit(main()), call main(). Here is what main() does, function by function.

flowchart TD
    A["main()"] --> B["parse_args()<br/>read options like -v, -t, --graph"]
    B --> C["TravelPlanner()<br/>runs __init__"]
    C --> D["Settings.from_env()<br/>load .env"]
    D --> E{"require_keys()<br/>all 3 keys present?"}
    E -- "no" --> X["print error, exit with code 1"]
    E -- "yes" --> F["create_llm()<br/>ChatOpenAI model"]
    F --> G["create_internet_search()<br/>Tavily tool"]
    G --> H["create_itinerary_tool()<br/>wraps the deep agent"]
    H --> I["build_travel_planner_graph()<br/>wire nodes + edges, compile"]
    I --> J{"Which mode?"}
    J -- "--graph" --> K["print Mermaid diagram"]
    J -- "a question was typed" --> L["answer() once"]
    J -- "nothing typed" --> M["chat()<br/>loop: input → answer()"]
    L --> N["planner.run()<br/>graph.invoke(...)"]
    M --> N
Key point. Building the planner makes no paid API calls. It only creates objects. The paid calls start inside graph.invoke(...), when the graph actually runs.

The graph: nodes and edges

LangGraph runs your program as a map of steps. Each node is a normal Python function that receives the shared state (a dictionary) and returns the parts it wants to change. Edges decide which node runs next. Solid arrows always happen; dotted arrows are decisions.

flowchart TD
    START(["START"]) --> O["orchestrator"]
    O -. "Send (parallel)" .-> SA["search_agent_node"]
    O -. "Send (parallel)" .-> PA["planner_agent_node"]
    SA -. "wants a tool" .-> ST["search_tool_node"]
    ST --> SA
    SA -. "finished" .-> SY["synthesizer"]
    PA -. "wants a tool" .-> PT["planner_tool_node"]
    PT --> PA
    PA -. "finished" .-> SY
    SY --> END(["END"])

orchestrator

Asks the AI to fill in a ClassificationResult: a list of tasks, at most one per agent. It also clears last turn's results so they don't leak into this answer.

graph.py · orchestrator()

dispatch_to_agents

Not a node; it's the decision on the orchestrator's arrows. It returns one Send per task, which starts the agents at the same time.

graph.py · dispatch_to_agents()

search_agent_node

Talks to the AI using the flight/hotel prompt. The AI either asks to call a tool or gives its final answer.

graph.py · search_agent_node()

search_tool_node

Runs the tool the AI asked for (search_flights or search_hotels) and stores the result, then goes back to the agent.

graph.py · search_tool_node()

planner_agent_node

Same pattern with the travel-scout prompt. Its tools are web search and the itinerary deep agent.

graph.py · planner_agent_node()

planner_tool_node

Runs tavily_search or itinerary_research_agent. The itinerary agent is a whole agent of its own, so this can take a minute.

graph.py · planner_tool_node()

synthesizer

Counts results. If an agent is still working it returns {} (no change) and waits. With one result it passes it through; with two it asks the AI to merge them.

graph.py · synthesizer()

route_search / route_planner

The small decision functions on the dotted arrows. They look at the agent's last message: tool calls → go to the tool node, otherwise → synthesizer.

graph.py · route_search(), route_planner()

How the state changes along the way

The state is one Python dictionary that every node can read. Each row shows what a node writes into it.

StepNodeWhat it writes into the state
0run()user_query = your text; messages gets your question added to the chat history.
1orchestratortasks = 2 AgentTask objects; agent_results, search_messages, planner_messages are emptied for this turn.
2search_agent_nodesearch_messages += your sub-question and the AI's reply, which asks for search_hotels.
2planner_agent_nodeplanner_messages += sub-question and a reply asking for itinerary_research_agent. Runs in the same step as the search agent.
3both tool nodesEach adds a ToolMessage with the tool's output to its own message list.
4both agent nodesThe AI reads the tool output and writes a final answer. Each adds one entry to agent_results.
5synthesizerfinal_answer = merged text; messages += the answer, so the next question can refer back to it.
Why two lists of messages? The two agents run at the same time. If they wrote into one shared list, their messages would get mixed up. So each agent has its own private list: search_messages and planner_messages.
Stop 6

The agent ↔ tool loop

Both agents work the same way. The AI can't search the internet itself. It replies with a request ("please call search_hotels with these arguments"). Our code runs the function and hands the result back. This repeats until the AI answers without asking for a tool.

flowchart TD
    A["agent node calls the AI<br/>prompt + messages so far"] --> B{"Does the reply contain tool_calls?"}
    B -- "yes" --> C["tool node<br/>_run_tool_calls() runs each function"]
    C --> D["add ToolMessage with the result"]
    D --> A
    B -- "no" --> E["save reply in agent_results"]
    E --> F["go to synthesizer"]

Safety net: --recursion-limit (default 50) stops the loop if it ever runs too many steps.

Python ideas used in this code

Open any card to see a real line from the project and what it means.

Importsevery file 
from langchain_openai import ChatOpenAI
from travel_planner.config import Settings

Load a name from another module so you can use it here. The first line loads from an installed package (that's why it must be in requirements.txt). The second loads from our own folder travel_planner/config.py.

Type hintsevery file 
def create_itinerary_tool(llm: BaseChatModel, internet_search: BaseTool) -> BaseTool:

The parts after : and -> say what type each value should be. Python does not enforce them while running; they help you and PyCharm understand the code and catch mistakes. Optional[str] means "a string or None".

from __future__ import annotations at the top of each file lets newer hint styles like str | None work everywhere.

Dataclass and @classmethodconfig.py 
@dataclass(frozen=True)
class Settings:
    openai_api_key: str | None
    chat_model: str = DEFAULT_CHAT_MODEL

    @classmethod
    def from_env(cls) -> "Settings":
        ...
        return cls(openai_api_key=..., ...)

@dataclass writes the boring parts of a class for you, such as the __init__ that stores each field. @classmethod makes a method you call on the class itself; cls is the class, so cls(...) creates a new Settings. This is a common pattern for "create an object from somewhere", here from environment variables.

Pydantic models and Fieldtools.py, graph.py 
class AgentTask(BaseModel):
    source: Literal["search_agent_node", "planner_agent_node"]
    user_query: str
    focus: str = Field(default="", description="What aspect this agent should focus on")

A class that checks its data. If the AI returns source="hotel_agent", Pydantic rejects it because Literal[...] allows only those two strings. Field(...) sets a default and a description the AI reads. Field(...) with three dots means "required, no default".

TypedDict, Annotated and reducersgraph.py 
class TravelPlannerState(TypedDict, total=False):
    agent_results: Annotated[List[dict], extend_or_reset]
    final_answer: str

TypedDict describes a dictionary's keys. Annotated[type, extra] attaches extra info to a type; LangGraph uses it to learn how to combine updates. For agent_results, the extra is the function extend_or_reset, called a reducer:

def extend_or_reset(existing, update):
    if update is None:
        return []                         # None means "clear the list"
    return (existing or []) + list(update)  # otherwise append

So when both agents return a result at the same time, both are appended instead of one overwriting the other. Keys without a reducer, like final_answer, are simply replaced.

Decorators like @tooltools.py, agents.py 
@tool(args_schema=HotelSearchInput)
def search_hotels(location: str, check_in_date: str, ...) -> str:
    """Search for hotels in a location (Google Hotels via SerpAPI)."""

A line starting with @ wraps the function below it. @tool turns a normal function into a LangChain tool object that the AI can be told about. The tool's name comes from the function name, and its description comes from the docstring (the text in triple quotes), so docstrings matter here.

Functions inside functions (closures)graph.py, agents.py 
def build_travel_planner_graph(llm, search_tools, planner_tools, checkpointer=None):
    search_model = llm.bind_tools(search_tools)

    def search_agent_node(state):
        response = search_model.invoke(...)   # uses search_model from outside
        ...

A function defined inside another function can use the outer function's variables, even after the outer one has finished. That's how every node gets access to llm and the tools without global variables. It also lets the tests pass in a fake AI instead of OpenAI.

dict.get() and default valuesgraph.py 
history = list(state.get("search_messages") or [])

state["key"] crashes if the key is missing; state.get("key") returns None instead. x or [] means "use x, but if it's empty or None, use an empty list". Together they make the code safe when a value hasn't been set yet.

List and dict comprehensionsgraph.py, tools.py 
search_tools_by_name = {t.name: t for t in search_tools}

A one-line loop that builds a collection. This builds a dictionary like {"search_flights": <tool>, "search_hotels": <tool>}, so the tool node can find a tool by the name the AI asked for. The same thing written as a normal loop:

search_tools_by_name = {}
for t in search_tools:
    search_tools_by_name[t.name] = t
f-stringseverywhere 
sub_query += f"\n\nFocus on: {task.focus}"

A string starting with f fills in anything inside { } with its value. \n is a new line.

try / excepttools.py, graph.py, main.py 
try:
    results = GoogleSearch(params).get_dict()
    ...
except Exception as exc:
    return json.dumps({"error": str(exc)})

Run the code under try; if anything goes wrong (no internet, bad key), jump to except instead of crashing. Here the error is turned into text the AI can read and explain to you.

Generators and yieldgraph.py 
def stream_updates(self, query, thread_id=None, ...):
    for chunk in self.graph.stream(...):
        for node, update in chunk.items():
            yield node, update

yield hands back one value at a time while the function keeps running. main.py uses this with -v to print each node's name as soon as it finishes, instead of waiting for the whole answer.

self and methodsgraph.py 
planner = TravelPlanner()        # runs __init__(self, ...)
planner.ask("Best time to visit Jaipur?")  # inside ask, self is planner

__init__ runs once when the object is created and stores things on self, like self.graph. Every method receives the object as its first argument, self, so ask() can call self.run(), which uses self.graph.

if __name__ == "__main__"main.py 
if __name__ == "__main__":
    sys.exit(main())

True only when you run the file directly (python main.py), not when another file imports it. sys.exit(0) means success; 1 means an error, which scripts and terminals can check.

Suggested reading order

  1. config.py: short, and shows a class, a dataclass and a custom error.
  2. tools.py: plain functions that call an API and return JSON. Ignore the long dictionaries; follow params → GoogleSearch → output.
  3. prompts.py: skim it. It's English instructions for the AI, and it explains what each agent is supposed to do.
  4. agents.py: how the AI model and the itinerary agent are created.
  5. graph.py: read the module docstring first, then each node function, then the "Wiring" block near the end. Keep the Stop 4 diagram open next to it.
  6. main.py: how it all gets started from the terminal.
  7. tests/test_graph.py: shows the graph running with a fake AI. Set a breakpoint in a node and run pytest from PyCharm to watch the state change step by step.
Try this. Run python main.py -v "What is the best time to visit Jaipur?". The ✓ lines show the nodes from Stop 4 as they run, and the end shows the tasks and agent results from Stop 5.

Words you'll see

LLM
Large language model, the AI (here an OpenAI model) that reads text and writes text.
Agent
An LLM with instructions (a prompt) and tools it may call.
Tool
A Python function the AI can ask us to run, like search_hotels.
Prompt
The instructions sent to the AI before your question.
State
The shared dictionary every node reads from and writes to.
Node
One step in the graph; a Python function.
Edge
A connection that decides which node runs next.
Send
LangGraph's way to start a node with its own input, so several nodes can run in parallel.
Checkpointer
Saves the state after each turn, so follow-up questions in the same thread_id remember earlier ones.
thread_id
The name of one conversation. Same id means shared memory.
Reducer
A function that decides how a new value is combined with the old one (append, clear, or replace).
